================================================================================

1.1 Executive Summary
AISaraj is an enterprise-grade, automated technical interview and evaluation platform
engineered to bridge the gap between engineering candidates and rigorous technical screening.
Traditional hiring pipelines suffer from severe bottlenecks: senior engineers spend hundreds
of unscalable hours conducting repetitive first-round technical screenings, candidates experience
anxiety and subjective human biases, and companies bear astronomical financial costs per hire.
AISaraj transforms this paradigm by deploying an autonomous, voice-interactive AI Interviewer
that conducts real-time verbal technical rounds, administers live algorithmic coding challenges,
enforces automated computer vision proctoring, and produces mathematically calibrated evaluation
reports powered by Google's Gemini Large Language Model (LLM).

1.2 Key Differentiators & Platform Capabilities
- Dual Authentication Architecture: Seamless onboarding supporting both traditional salted bcrypt
  email/password credentials and Google OAuth 2.0 OpenID Connect (OIDC) identity federation.
- Real-Time Voice Synthesis & Transcription: High-fidelity verbal dialogue powered natively by
  the browser's Web Speech API (SpeechSynthesis and SpeechRecognition), operating with zero external
  voice latency and zero cloud audio bandwidth overhead.
- Dual Operational Modes:
    a) Recruiter-Scheduled Interviews: Human interviewers schedule customized sessions with tailored
       difficulty levels, deadlines, and technical tracks; candidates receive dashboard alerts and
       undergo structured multi-question examinations.
    b) Candidate Self-Practice & LeetCode Sandbox: Candidates launch autonomous practice tracks
       across Frontend, Backend, Fullstack, Core CS, and Data Structures & Algorithms (DSA),
       receiving dynamic instant feedback and code compilation.
- Subprocess Code Execution Engine: Multi-language isolated sandbox capable of compiling and
  executing Python, JavaScript, C++, and Java code with strict memory, standard input (stdin), and
  wall-clock timeout safety guards.
- Client-Side Neural Computer Vision Proctoring: Integrated Face-API.js running a pre-trained
  TinyFaceDetector convolutional neural network (CNN) within the client's browser, tracking facial
  orientation, detecting absence, flagging multi-face intrusions, and monitoring tab-switching
  violations with a 3-strike disqualification rule.
- Comprehensive 5-Dimensional AI Evaluation: Gemini AI dynamically scores completed transcripts
  across Communication, Technical Depth, Code Quality, Optimization, and Problem Solving on a 0-100
  spectrum, delivering actionable strengths, weaknesses, study roadmaps, and hiring recommendations.

4. AUTHENTICATION & AUTHORIZATION DEEP DIVE
================================================================================

4.1 Manual Credential Architecture (Email + Password)
1. Password Hashing with Bcrypt:
   - Plaintext passwords are NEVER stored in the database.
   - When a candidate registers, Passlib passes the plaintext password through the Blowfish-based
     bcrypt algorithm using a work factor (cost) of 12 rounds with a cryptographically randomized 128-bit
     unique salt.
   - The resulting hash (formatted as: $2b$12$[22_char_salt][31_char_hash]) is written to PostgreSQL.
   - During login, the server re-hashes the incoming password against the extracted salt; if the output
     hash matches, authentication succeeds in O(1) mathematical verification time.

2. JSON Web Token (JWT) Anatomy & Cryptographic Signing:
   - Upon successful verification, FastAPI mints an Access Token consisting of three Base64URL-encoded
     segments separated by dots: Header.Payload.Signature.
   - Segment 1 (Header): {"alg": "HS256", "typ": "JWT"}. Specifies HMAC using SHA-256 hash algorithm.
   - Segment 2 (Payload / Claims):
     {
       "sub": "42",                  // Subject (User ID in Database)
       "email": "candidate@saraj.ai",// Verified user email
       "role": "student",            // Role-based access control level
       "exp": 1759500000             // Expiration timestamp (epoch seconds)
     }
   - Segment 3 (Cryptographic Signature):
     HMACSHA256(Base64URL(Header) + "." + Base64URL(Payload), SECRET_KEY)
   - The SECRET_KEY is a 256-bit cryptographically secure string generated via Python `secrets.token_hex(32)`.
     Because only the server possesses the SECRET_KEY, any client-side tampering with claims immediately
     invalidates the signature, causing the server to reject the token with HTTP 401 Unauthorized.

4.2 Google OAuth 2.0 & OpenID Connect (OIDC) Integration
1. The Problem Solved: Eliminates password friction and offloads credential security to Google.
2. The Complete Flow:
   - User clicks "Sign in with Google" on React frontend.
   - The Google Identity Services SDK displays Google's secure popup dialog.
   - Candidate authenticates with Google servers; your app never touches the user's Google password.
   - Google signs and issues a Google ID Token (an OIDC JWT signed with Google's private RSA keys).
   - React sends this Google ID Token to FastAPI via `POST /api/v1/auth/google`.
   - FastAPI uses Google's public cryptographic keys (`google.oauth2.id_token.verify_oauth2_token`)
     to verify that:
       a) The signature matches Google's public key certificate.
       b) The audience (`aud`) strictly matches `settings.GOOGLE_CLIENT_ID`.
       c) The token has not expired.
   - FastAPI extracts verified claims (`email`, `given_name`, `picture`).
   - Just-in-Time (JIT) Provisioning: FastAPI checks PostgreSQL. If the email exists, it logs the user in;
     if not, it creates a new User record with a randomized, unguessable password hash.
   - FastAPI discards the Google ID Token and issues its OWN Application Access Token signed with its
     `SECRET_KEY`, unifying all subsequent API access under the same token format.

4.3 Access Token vs. Refresh Token Lifecycle & Silent Refresh
- Access Token: Short-lived (15 to 60 minutes). Transmitted in the HTTP Header:
  `Authorization: Bearer <token>` on every protected API call.
- Refresh Token: Long-lived (7 to 30 days). Stored securely in an `HttpOnly`, `SameSite=Strict`, `Secure`
  cookie inaccessible to malicious JavaScript scripts (immune to Cross-Site Scripting / XSS).
- Silent Refresh Pipeline:
  When an access token expires mid-session, an API request returns HTTP 401. The frontend Axios
  response interceptor catches this error before the user notices, quietly posts the Refresh Token
  to `POST /api/v1/auth/refresh`, receives a new 15-minute Access Token, and re-executes the failed
  request transparently.

6. QUESTION MANAGEMENT ARCHITECTURE: RAM VS. DATABASE VS. REDIS
================================================================================

6.1 Current Architecture: Hybrid In-Memory Pool with Session Freezing
AISaraj utilizes an optimized two-stage question management model:
- Stage 1 (The Question Library): Stored in server memory via `verbal_question_bank.py` containing
  50+ industry-verified questions per technical discipline.
- Stage 2 (The Frozen Candidate Paper): The moment an interview starts, 8 questions are selected,
  shuffled, and written to PostgreSQL table `ai_interview_questions`.

6.2 Engineering Trade-Off Analysis: Why This is Faster

+-------------------------------+----------------------------+-----------------------------+
| Architectural Metric          | AISaraj Current Hybrid     | Pure Database (No Redis)    |
+-------------------------------+----------------------------+-----------------------------+
| Location of Master Library    | Application RAM (Memory)   | Cloud PostgreSQL Disk       |
| Retrieval Latency (Selection) | 0.0001 ms (CPU RAM access) | 70-120 ms (Network SQL RTT) |
| SQL Randomization Overhead    | Python random.shuffle (0ms)| SQL ORDER BY RANDOM() (slow)|
| Total Network Trips to Start  | Exactly 1 trip (INSERT)    | Exactly 2 trips (SEL + INS) |
| Response Latency to Candidate | ~30 milliseconds total     | ~160-220 milliseconds total |
+-------------------------------+----------------------------+-----------------------------+

6.3 The Role of Redis in Scaling
- Why Redis is Not Mandatory Today: PostgreSQL easily handles thousands of reads per second with
  standard indexing. For current traffic levels, running an extra Redis cache adds unnecessary
  infrastructure costs and maintenance complexity.
- How Redis is Used in Enterprise V2:
  In an enterprise setup where non-engineers need to edit questions via an Admin CMS, the master questions
  are moved from Python code to a database table `question_bank`. To prevent 10,000 concurrent students
  from overwhelming the database on Monday morning, active question pools are cached in Redis RAM.
  This delivers the sub-millisecond retrieval speed of AISaraj's current code setup while allowing
  zero-downtime question edits in the database.

7. REAL-TIME AUDIO PIPELINE: WEB SPEECH API DEEP DIVE
================================================================================

7.1 Architecture of the Client-Side Voice Engine
Voice interaction is powered natively by the HTML5 Web Speech Specification, split into two modules:
1. SpeechSynthesis (Text-to-Speech / TTS):
   - Browser global controller: `window.speechSynthesis`.
   - Constructs a `SpeechSynthesisUtterance` object containing the question text.
   - Configures vocal properties: pitch (1.0), rate (1.0), volume (1.0), and preferred voice accent
     (en-US natural).
   - Audio rendering occurs on the client's local operating system audio subsystem.

2. SpeechRecognition (Speech-to-Text / STT):
   - Browser constructor: `window.SpeechRecognition || window.webkitSpeechRecognition`.
   - Captures microphone audio stream via WebAudio driver.
   - Operates in `continuous = true` and `interimResults = true` mode, outputting real-time partial
     text transcripts into React state as the candidate speaks.

7.2 Why Browser-Native Web Speech Beats Server-Side Cloud Audio
- Latency Elimination: Server-side voice models (such as ElevenLabs or AWS Polly) require sending text
  over the internet, waiting for remote neural audio synthesis, downloading heavy binary audio streams
  (MP3/WAV), and buffering before playback (introducing 800ms - 2000ms delay). Web Speech API speaks in 0ms.
- Bandwidth & Server Cost: Server audio streaming at 10,000 users requires gigabytes of bandwidth and
  costs thousands of dollars in cloud API bills. Web Speech API runs 100% free on client hardware.

9. AUTOMATED PROCTORING & COMPUTER VISION ENGINE (FACE-API.JS + ML)
================================================================================

9.1 Technology Stack & Machine Learning Model
- Vision Framework: Face-API.js v0.22.2 (TensorFlow.js WebAssembly / WebGL backend).
- Neural Network Architecture: TinyFaceDetector, an ultra-lightweight, quantized single-shot
  convolutional neural network (MobileNet-style depthwise separable convolutions).
- Weight Storage: `frontend/public/models/tiny_face_detector_model-*` loaded locally in the browser
  via `faceapi.nets.tinyFaceDetector.loadFromUri('/models')`.

9.2 Detection Pipeline & Violation Logic
Proctoring runs continuously across two parallel event loops in `AIPracticePage.jsx`:
1. Facial Presence & Head Pose Tracking:
   - Interval runs `faceapi.detectSingleFace(videoElement, new faceapi.TinyFaceDetectorOptions({ inputSize: 320, scoreThreshold: 0.28 }))`.
   - Bounding Box Verification: Computes face center `(x + width/2) / videoWidth` and `(y + height/2) / videoHeight`.
   - Absence & Looking-Away Timer: If no face is detected or face orientation wanders outside boundaries
     for more than 4 consecutive seconds, a proctoring violation triggers.

2. Browser Tab-Switching & Visibility Monitoring:
   - Listens to Page Visibility API (`document.hidden`) and window blur events (`window.onblur`).
   - If the candidate switches tabs, minimizes the window, or attempts to open ChatGPT / Google,
     an instant strike is registered.

9.3 Strike System & Disqualification Mathematics
- Three-Strike Disqualification Rule:
  * Warning 1: Audio/visual modal alert displayed on screen.
  * Warning 2: High-priority warning alert; interview timer continues.
  * Warning 3: Automatic instant interview termination (`disqualified = true`).
- Proctoring Score Formula:
  `proctoring_score = max(0, 10 - (warning_count * 3))`
  * 0 Warnings: 10 / 10 (Full integrity)
  * 1 Warning:   7 / 10
  * 2 Warnings:  4 / 10
  * 3 Warnings:  0 / 10 (Immediate disqualification sent to Gemini evaluation report).

10. CODE EXECUTION SANDBOX ENGINE
================================================================================

10.1 Architecture
The code execution engine (`backend/services/code_executor.py`) provides safe, sandboxed execution
for candidate algorithmic programming challenges.
- Supported Languages: Python 3, JavaScript (Node.js), C++ (g++), Java (OpenJDK).
- Frontend Interface: Monaco Code Editor (`@monaco-editor/react`) embedded in the interview room.

10.2 Sandboxed Execution Mechanics
1. Code Submission: Frontend posts `{ language: "python", source_code: "def twoSum...", stdin: "[2,7,11,15]
9" }`
   to `POST /api/v1/code/execute`.
2. Temporary File Isolation: The backend generates an isolated scratch file with a UUID.
3. Subprocess Spawning: Spawns an isolated asynchronous OS subprocess using `asyncio.create_subprocess_exec()`.
4. Resource Limits:
   - Wall-Clock Timeout: 5.0 seconds maximum execution time. If code enters an infinite loop
     (`while True: pass`), the process is forcefully killed via `proc.kill()` and returns:
     `{"stderr": "Execution timed out (5s limit)", "exit_code": 124}`.
   - Memory & Output Capping: Stdout and Stderr are truncated at 10,000 characters to prevent buffer
     overflow attacks.

11. END-TO-END EXECUTION FLOW: START-TO-FINISH LIFECYCLE
================================================================================

Step 1: Recruiter Scheduling / Candidate Selection
- Recruiter logs in -> visits `/schedule` -> submits track, difficulty, deadline, and candidate ID.
- FastAPI writes new row to `ai_scheduled_interviews` with status `scheduled`.

Step 2: Candidate Dashboard Notification
- Candidate logs in -> Dashboard calls `GET /api/v1/ai_interviews/student` -> displays upcoming interview card.

Step 3: Launching Interview Room & Session Freezing
- Candidate clicks "Start Interview" -> `POST /api/v1/ai_interviews/{id}/start`.
- FastAPI updates status to `in_progress`, selects 8 questions from `verbal_question_bank.py`,
  and commits them as permanent records in `ai_interview_questions`.

Step 4: Real-Time Audio Delivery
- React calls `POST /api/v1/ai_interviews/{id}/questions/next` -> receives Question 0 JSON.
- React feeds string into `window.speechSynthesis.speak()` -> computer speakers ask question out loud.

Step 5: Candidate Voice Capture & Live Transcription
- Candidate speaks -> `window.webkitSpeechRecognition` captures microphone input -> transcribes speech
  into text inside the answer textarea in real time.

Step 6: Real-Time Clarification (Optional)
- Candidate says "Could you repeat that?" -> Backend regex matches `repeat_triggers` -> Gemini generates
  1-sentence clarification -> Web Speech API speaks it aloud.

Step 7: Answer Submission & Next Prompt
- Candidate clicks "Submit Answer" -> `POST /api/v1/ai_interviews/{id}/submit`.
- FastAPI saves answer to `ai_interview_answers` -> fetches Question 1 -> Web Speech speaks Question 1.
- Loop repeats until all 8 questions are answered.

Step 8: Interview Completion & AI Evaluation
- Candidate submits last question -> `POST /api/v1/ai_interviews/{id}/complete`.
- FastAPI retrieves complete transcript from PostgreSQL -> formats Master Prompt -> calls Google Gemini.
- Gemini evaluates the transcript across 5 dimensions on a 0-100 scale -> returns structured JSON.
- FastAPI writes record to `ai_interview_reports` -> marks interview `completed`.

Step 9: Final Scorecard Presentation
- React receives report JSON -> renders Report Card dashboard with animated score dials, strengths,
  weaknesses, study roadmap, and Hiring Signal badge.

15. MASTER INTERVIEW & VIVA PREPARATION: TOP 50 TECHNICAL Q&A
================================================================================

Q01: What is the core problem AISaraj solves?
A01: It eliminates the expensive, unscalable, and biased technical screening bottleneck by providing
     an autonomous AI interviewer that conducts voice rounds, coding evaluations, and automated proctoring.

Q02: Why did you choose FastAPI over Django or Flask?
A02: FastAPI is built on Starlette and Pydantic, offering native asynchronous async/await support,
     blazing-fast performance comparable to Go/Node.js, automatic OpenAPI documentation, and strict
     data serialization.

Q03: How does passlib with bcrypt ensure password security?
A03: It applies the Blowfish-based bcrypt algorithm with an automatic random 128-bit salt and 12 work
     rounds, making brute-force dictionary and rainbow-table attacks computationally impossible.

Q04: What is the structure of a JSON Web Token (JWT)?
A04: It consists of three Base64URL-encoded parts: Header (algorithm & type), Payload (claims like
     sub, email, exp), and Signature (cryptographic hash created with the server's SECRET_KEY).

Q05: Can a JWT be decrypted by anyone?
A05: Yes, Base64URL decoding is trivial. JWTs are signed for integrity, not encrypted for secrecy.
     Sensitive data (like passwords) must never be placed inside the payload.

Q06: How do you verify Google OAuth tokens on the backend?
A06: We pass the Google ID Token to `google.oauth2.id_token.verify_oauth2_token()`, which validates
     Google's cryptographic signature using Google's public certs and verifies that the audience (aud)
     matches our GOOGLE_CLIENT_ID.

Q07: What is the difference between Google ID Token and App Access Token?
A07: Google ID Token is an identity assertion issued by Google proving who the user is. Your App Access
     Token is an authorization token issued by your backend to allow access to your own protected APIs.

Q08: Why use both Access Tokens and Refresh Tokens?
A08: To balance security and UX. Access tokens are short-lived (15m) so stolen tokens expire quickly;
     Refresh tokens are long-lived (7d) and kept in secure HttpOnly cookies to silently renew access.

Q09: What is Silent Refresh?
A09: When an access token expires, an Axios interceptor catches the 401 response, calls `/auth/refresh`
     with the refresh token, gets a new access token, and retries the original request without user interruption.

Q10: Why did you choose PostgreSQL over MongoDB?
A10: Technical interviews require strict relational integrity (users -> interviews -> questions -> answers -> reports),
     ACID transactional guarantees, and foreign-key cascade protections best served by a relational database.

Q11: What is the role of Alembic in this project?
A11: Alembic manages version-controlled database schema migrations, auto-generating migration scripts
     from SQLAlchemy model changes and applying them without data loss.

Q12: Why are interview questions stored in Python code initially instead of purely in PostgreSQL?
A12: Pulling from an in-memory Python dictionary takes 0.0001ms (RAM speed) with zero network latency,
     requiring only 1 single database trip to save the session questions. Querying PostgreSQL directly
     would require 2 separate network trips (~150ms+).

Q13: Why are questions copied to PostgreSQL when an interview starts?
A13: To freeze the exam paper against browser refreshes, preserve sequential order, provide stateless
     backend continuity, and generate Primary Key IDs for foreign-key answer linking.

Q14: What is the purpose of Redis in this architecture?
A14: Redis is an optional in-memory cache. In a system where master questions live in a database table,
     Redis caches active pools in RAM, preventing thousands of concurrent users from overloading the database.

Q15: How does the Web Speech API work in your app?
A15: It runs natively in the browser: `speechSynthesis` converts question text into voice through the
     speakers (TTS), while `webkitSpeechRecognition` captures microphone audio into text (STT).

Q16: Why use Web Speech API instead of server-side TTS like ElevenLabs?
A16: It operates with zero latency (instant audio playback), consumes zero server bandwidth, and is
     100% free with no third-party API costs.

Q17: What model of Google Gemini is used and why?
A17: `gemini-1.5-flash`, because it offers ultra-fast token response times, a massive context window,
     strong logical reasoning for code evaluation, and high cost-efficiency.

Q18: How does the backend force Gemini to return valid JSON?
A18: By setting `response_mime_type="application/json"` in the generation configuration and explicitly
     defining the required JSON key schema in the prompt.

Q19: When does Gemini get called during an interview?
A19: It is called only twice: conditionally when the candidate asks for question repetition/clarification,
     and unconditionally at the very end to evaluate the full interview transcript.

Q20: How does the backend detect if a candidate asked to repeat a question?
A20: An intelligent keyword pattern matcher checks the transcribed text for triggers ('repeat', 'pardon',
     'say again'). If matched, it routes to Gemini for a 1-sentence clarification instead of saving an answer.

Q21: What machine learning library powers automated proctoring?
A21: Face-API.js v0.22.2 running on TensorFlow.js directly inside the client's browser.

Q22: Which ML model is used for face detection?
A22: TinyFaceDetector, an ultra-lightweight, quantized convolutional neural network optimized for fast
     browser inference.

Q23: How does proctoring detect looking away or absence?
A23: It continuously runs face detection against the live webcam stream, calculating bounding box coordinates.
     If no face is detected or head orientation wanders off-center for 4+ seconds, a warning triggers.

Q24: How does tab-switching detection work?
A24: It listens to the Page Visibility API (`document.hidden`) and `window.onblur`. If the candidate leaves
     the tab, an instant violation strike is recorded.

Q25: What is the proctoring disqualification policy?
A25: A 3-warning strike rule. On the third warning, the interview is immediately terminated and marked disqualified.

Q26: How is the proctoring score calculated?
A26: Using the mathematical formula: `proctoring_score = max(0, 10 - (warning_count * 3))`.

Q27: How is code safely executed on the backend?
A27: Using asynchronous subprocesses (`asyncio.create_subprocess_exec`) with strict 5-second wall-clock
     timeouts and output size truncation to prevent infinite loops and memory exhaustion.

Q28: What code editor is embedded in the frontend?
A28: Monaco Editor, the web engine powering Microsoft Visual Studio Code.

Q29: What happens if a candidate's internet disconnects mid-interview?
A29: Because the interview session and questions are frozen in PostgreSQL, the candidate simply refreshes
     and resumes at the exact question where they left off without losing progress.

Q30: What are the 5 evaluation dimensions Gemini grades?
A30: Communication, Technical Depth, Code Quality, Optimization, and Problem Solving.

Q31: What hiring signals does Gemini output?
A31: 'Strong Hire' (90+), 'Hire' (75-89), 'Consider' (60-74), and 'No Hire' (<60).

Q32: What is the role of `backend/api/deps.py`?
A32: It provides reusable FastAPI dependency injection functions, primarily `get_current_user` which
     validates the Bearer JWT and protects endpoints.

Q33: What is the role of `frontend/src/api/client.js`?
A33: It configures the Axios HTTP instance and houses the request interceptor that injects JWT tokens
     into every outgoing request.

Q34: How do React Context Providers work in AISaraj?
A34: AuthContext manages user authentication state globally, while AISessionContext manages live interview
     questions, timers, and transcripts across components without prop drilling.

Q35: What is CORS and how is it configured in FastAPI?
A35: Cross-Origin Resource Sharing. Configured via CORSMiddleware in `main.py` to allow frontend origins
     (localhost:3000, vercel.app) to make authorized HTTP requests to the backend.

Q36: What is Pydantic and how is it used here?
A36: Pydantic is a Python data validation library. It defines schemas that parse, validate, and serialize
     request bodies and response payloads.

Q37: What is asyncpg and why is it used?
A37: asyncpg is a high-performance asynchronous PostgreSQL database driver for Python, maximizing
     concurrency under heavy I/O loads.

Q38: What is SQLAlchemy 2.0 selectin loading?
A38: It is an asynchronous relationship loading strategy (`lazy="selectin"`) that fetches related objects
     using a secondary SELECT IN query, avoiding the classic N+1 query problem.

Q39: How does the system handle candidate silence or no answers?
A39: If no substantive spoken words or code are detected in the transcript, the backend bypasses Gemini
     and assigns a calibrated score of 0 with 'No Hire' and targeted constructive feedback.

Q40: How is a peer-to-peer human interview conducted?
A40: Using WebRTC (RTCPeerConnection) to establish a direct peer-to-peer audio/video mesh between the
     interviewer and candidate with minimal server relay.

Q41: What is the purpose of `pyrefly.toml` in the project?
A41: It configures search paths (`search-path = ["backend"]`) and virtual environments for the Pyrefly
     static type checker so module imports resolve cleanly.

Q42: What is the purpose of `vercel.json` in the frontend?
A42: It contains URL rewrite rules ensuring that all deep client-side routes (like `/ai-interview/42`)
     are served by `index.html` without returning 404 on page reload.

Q43: What security headers should be used in production?
A43: Strict-Transport-Security (HSTS), X-Content-Type-Options, X-Frame-Options, and Content-Security-Policy (CSP).

Q44: How are database transactions handled in FastAPI?
A44: Using SQLAlchemy async sessions inside an `async with` context manager or FastAPI dependency,
     committing on success and automatically rolling back on exceptions.

Q45: Can Gemini's evaluation be biased? How is it standardized?
A45: The prompt enforces strict rubric directives across the 0-100 scale with concrete score brackets,
     minimizing temperature variability and standardizing evaluation across all candidates.

Q46: How are environment variables isolated between development and production?
A46: Development uses local `.env` files; production uses cloud provider environment key management
     (Render/Vercel dashboard) injected directly into runtime processes.

Q47: What is the benefit of single-page application (SPA) architecture for an interview app?
A47: Eliminates full page reloads, preserves audio and webcam streams continuously, and provides smooth
     desktop-app-like responsiveness during intense technical interviews.

Q48: What is the maximum wall-clock execution time for code in the sandbox?
A48: 5.0 seconds. Any code running longer is terminated to protect system resources.

Q49: How does Just-in-Time (JIT) provisioning work during Google login?
A49: If a user logs in via Google for the first time, the backend automatically detects their absence in
     the `users` table and creates an account on the fly with a random password hash.

Q50: What are the three most impressive engineering highlights of AISaraj?
A50: 1) Client-side zero-latency voice interaction via Web Speech API;
     2) Browser-based neural network proctoring using quantized TinyFaceDetector;
     3) Asynchronous full-transcript evaluation pipeline combining FastAPI and Google Gemini 1.5 Flash.
